MCP 协议到底解决了什么问题：从一次失败的集成说起

我们花了三个月把工具的调用方式从「贴文档」改成「走协议」。这次失败让我明白：协议的价值不在连接，而在边界。

第一次集成是在四个月前。目标很简单：让模型能查我们的数据库。做法也很直接——把表结构打成一段文本塞进提示词，再让它写 SQL。

一、为什么「塞提示词」会先崩

三周之后问题开始堆积。表结构每次变更都要重新贴一遍；同一个问题在不同会话里得到不同答案；最要命的是，我们无法回答「模型到底碰过哪些数据」。

把工具塞进提示词，等于把工具的边界也交给了模型的自由发挥。

二、协议给的三个东西

  • 显式的能力声明：服务端先说清楚自己能做什么，客户端再决定放不放行。
  • 可枚举的权限：读写、联网、执行，是能被勾选和审计的字段，而不是一句自然语言。
  • 可替换的传输：stdio 适合本地，sse / http 适合共享。

三、我们现在的做法

所有 MCP 都登记在一张表里，权限写死为四个档位，卡片上直接给用户看。想接入新的服务，先填声明，再跑一次实测报告。
